| Без ограничений | 3/3 | 813.7 | 0/3 | 0/3 | свободный текст — парсинг JSON кодом не проходит |
| Явное описание формата в промпте | 3/3 | 301.7 | 0/3 | 0/3 | формат держится, но это не машинная гарантия |

| Stop sequence | 3/3 | 267.0 | 0/3 | 0/3 | модель игнорирует ЧАСТЬ1/STOPHERE — маркер не появляется, stop как контроль не проверяется |
| Строгая схема (response_format json_schema) | 3/3 | 496.7 | 3/3 | 0/3 | JSON парсится, но `uses` приходит string вместо array — strict schema не enforced |

## Выводы

1. **Без ограничений** — связный Markdown-текст (~740–860 символов). Для человека ок, для кода нет: `json.loads` **0/3**.
2. **Явный формат в промпте** — шаблон `SUMMARY/USES/FEATURES` соблюдён **3/3**, ответы короче и стабильнее. Но это soft-constraint: парсер всё равно свой (не JSON), гарантии API нет.
3. **max_tokens=40** — ломается **полнота**: `finish_reason=length` **3/3**, текст обрывается на полуфразе (`**Для чего используют`). Для структурированных данных бесполезен.
4. **stop sequence** — в этом прогоне **ломается замысел контроля**: модель не следует схеме `ЧАСТЬ1 → STOPHERE → ЧАСТЬ2`, маркер **0/3** раз не встретился. `finish_reason=stop` здесь совпадает с baseline (нормальное завершение у провайдера), а не доказательство срабатывания stop-маркера.
5. **json_schema / structured output** — лучший вариант для кода: `json.loads` **3/3** (даже из ````json` fences). Но **строгая схема ломается**: поле `uses` стабильно приходит как **string**, хотя в schema — `array[string]`; `schema OK 0/3`. На маршруте `wormsoft/agent/low` → `gemma4:31b-cloud` `strict: true` **не гарантирует** типы полей.
6. **Итог:** для машинного разбора — `response_format` + обязательная клиентская валидация схемы; промпт-формат удобен, но хрупок; `max_tokens` режет смысл; `stop` полезен только если маркер реально попадает в генерацию.
